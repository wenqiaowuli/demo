# 高中物理模型动画网页制作流程

## 1. 目的与适用范围

本流程用于依照人教版高中物理六册模型清单，制作“一页一个模型”的交互式动画演示网页。制作目标是物理正确、教学重点清楚、交互可验证、桌面与手机均可使用，并能按现有项目方式登记和发布。本工作流固定模型版本和各阶段责任；如果指定模型暂不可用，先记录并请用户确认替代型号，不自行静默更换。

## 2. GPT、Gemini、GLM、JEV 的分工

| 模型 | 主要职责 | 交付物 | 使用边界 |
|---|---|---|---|
| **GPT：`opencode-go/gpt-6-luna`** | 项目协调与主实现者；核对清单、定 PRD、实现物理计算与主页面、写测试、合并意见 | 定稿需求、主代码、测试矩阵、交付说明 | 唯一代码整合者；物理结论仍须教材对照和数值验证 |
| **Gemini：`google/gemini-3.1-pro-preview`** | 独立教材、物理和教学审阅；复核假设、公式、临界条件、误区和图文表达 | 带推导的审阅意见、遗漏场景清单 | Google 提供者；该目录当前列出为 preview。需提供教材版本/页面；须给出公式依据或反例，不泛泛判断 |
| **GLM：`opencode-go/glm-5.3`** | 交互方案、UI 草案、限定组件实现或独立代码审阅 | UI 草案、隔离补丁/组件、代码问题清单 | 不改物理规格；一次只做明确小任务，不与 GPT 并行覆盖同一文件 |
| **JEV：`jev-1.13`** | 对整理好的网页证据做结构化判断和评分，辅助发现风险 | 是/否、分类、评分及概率 | 非对话/代码生成模型，不执行网页、不访问 URL；结果无解释，不能替代人工、浏览器测试或计算 |

**版本依据**：2026-10-11 在当前 OpenCode 模型目录中核对到上述 GPT、Gemini、GLM ID；JEV 版本沿用 `docs/jev-model-usage.md`。如果后续模型目录变化，先单独更新本节并确认兼容性，再用于新网页，避免同一轮制作中混用版本。

| 测试与修复 | GPT `opencode-go/gpt-6-luna` 执行；Gemini `google/gemini-3.1-pro-preview` 复核测试覆盖 | 在当前候选版本上运行测试、截图核查和缺陷修复；其他模型不得替代真实浏览器执行。 |
| JEV 结构化复核 | JEV `jev-1.13` | 在实际测试之后，基于网页证据和测试结果做结构化复核；只作为交付前复查线索。 |
| 整理与交付 | GPT `opencode-go/gpt-6-luna` | 更新导航、同步 `_repo`、核对版本与验收文档；提交/推送需用户确认。 |

### 推荐协作原则

1. **GPT 负责形成唯一需求和唯一合并版本**，Gemini、GLM 的输出作为审阅材料或隔离补丁。
2. **先锁定物理模型，再做界面与编码**。若物理模型尚未通过复核，不进入视觉打磨。
3. **让审阅模型独立检查**：提供模型描述和候选网页证据，不先把 GPT 的结论当作正确答案给审阅者。
4. **以教材、方程推导、可复现测试为裁决依据**，不按模型投票决定物理结论。
5. 每一个新模型网页都走完同一组节点并调用表中固定版本；调用失败或版本不可用时记录阻塞，不跳过节点、不静默换模型。

## 3. 标准制作流程

### 阶段 0：选题与查重

**模型：GPT `opencode-go/gpt-6-luna`；范围由用户确认。**

1. 从 `../高中物理动画模型清单.md` 选定一个模型，记录教材册、章节、清单编号和是否为拓展模型。
2. 检查 `index.html` 与现有 HTML 演示页，确认是“尚无页面”“已有页面但缺关键功能”还是“已有页面可复用”。
3. 一页只设一个模型目标；多个阶段可以属于同一模型，但不能把不同模型硬塞进同一页。
4. 确认页面名称、文件名、主要使用对象和本轮非目标。

**本阶段输出：**模型卡片（名称、册/章、已有页面、制作/改造目标）。

### 阶段 1：教材知识点与物理模型定稿

**GPT `opencode-go/gpt-6-luna` 起草；Gemini `google/gemini-3.1-pro-preview` 独立复核；GPT 汇总后定稿。**

GPT 对单个模型整理：

- 研究对象、理想化条件和参考系；
- 初始条件、受力情况、约束关系、运动阶段；
- 核心方程、变量定义、正方向和单位；
- 状态切换与临界条件；
- 可观察量、图像和能量/动量关系；
- 高中生容易混淆的点及典型反例。

Gemini 重点检查：

- 公式推导、方向和正负号是否自洽；
- 边界情形、临界值、反向运动和特殊参数是否处理；
- 内容是否符合所用人教版教材，哪些属于高考拓展；
- 动画是否会诱发错误概念。

GPT 逐条处理 Gemini 的意见：确认、拒绝或标为待查，并留下理由。关键公式至少用手算、数值例子或单元测试之一独立验证。

**本阶段输出：**已确认的模型说明和拓展标注。未定稿前不写动画代码。

### 阶段 2：PRD 与验收标准

**GPT `opencode-go/gpt-6-luna` 编写；Gemini `google/gemini-3.1-pro-preview` 检查教学逻辑；GLM `opencode-go/glm-5.3` 提交交互草案。**

按项目已有需求文档的组织方式，写明：

1. 项目目标、教学重点和非目标；
2. 场景组成、动画状态及每阶段的物理量；
3. 可调参数、范围、默认值、单位和非法输入处理；
4. 播放、暂停、继续、重置、单步或进度回放等交互；
5. 受力矢量、轨迹、数值面板、公式卡和图像的显示规则；
6. 临界情况、端点行为、状态切换和异常参数处理；
7. 桌面、平板、手机布局和可读性要求；
8. 可量化的物理验收用例及界面验收用例。

参考文档：`docs/斜面物块运动演示网页需求.md`。该文档可借鉴其“典型场景 + 状态判断 + 测试矩阵 + 响应式验收”的结构，不必照搬不适用于当前模型的功能。

**本阶段输出：**需求文件及验收矩阵。需求变更时更新版本/修订记录，不能只在对话里口头改动。

### 阶段 3：画面与交互方案

**GLM `opencode-go/glm-5.3` 提出或搭建界面草案；GPT `opencode-go/gpt-6-luna` 决定并整合；Gemini `google/gemini-3.1-pro-preview` 检查教学可读性。**

先确定画面中的核心对象与动作，再决定控件：

- 动画中什么在运动、什么保持不动；
- 哪些力、速度、加速度或电/磁场量需要显示；
- 调参后画面、公式、读数和图像怎样同步更新；
- 哪些现象适合播放，哪些适合逐步暂停观察；
- 关键事件是否要提供场景预设或时间轴定位。

遵循项目现有网页的视觉与交互惯例：单页独立运行、Canvas 动画、清晰的播放控制、参数区、实时数据和必要图像；使用响应式布局、DPR 适配和窄屏换行。具体样式以相邻同类演示页为参照，不将旧页的物理假设或布局缺陷一并复制。

**本阶段输出：**页面草图/区块顺序、参数表、交互状态表。先确认方案，再开始完整实现。

### 阶段 4：实现与代码协作

**GPT `opencode-go/gpt-6-luna` 是唯一代码整合者；GLM `opencode-go/glm-5.3` 只处理拆分好的界面任务或独立补丁。**

1. 每个模型单独建立 HTML 页面；复杂模型可把计算与绘图拆成清晰函数，但不得把多个模型合并成一个页面。
2. 将物理计算写成可独立检查的状态更新函数；渲染函数只负责把状态画出来，避免计算和绘图互相污染。
3. 明确播放状态机，例如 idle、playing、paused、finished；对碰撞、到达端点、速度变号、共速等事件精确处理。
4. 控件变更后同步更新动画、图表、公式说明和实时读数；重置应恢复一致的初始状态。
5. GLM 如需写代码，先给它明确的文件、接口、不得改变的方程和验收条件；让它提交补丁或独立组件，由 GPT 检查并合并。
6. 不要让 GPT、Gemini、GLM 同时直接覆盖同一个工作文件。Gemini 通常只审阅，不作为共享分支上的并行写入者。

**本阶段输出：**可运行页面、更新的 PRD/修订记录、模型计算测试或测试方案。

### 阶段 5：独立审阅

#### Gemini / GLM 人工式审阅

给审阅者提供具体版本、需求和测试结果，要求以“文件位置/现象/物理或交互影响/可复现方式”报告问题。Gemini 优先复核物理和教学表达；GLM 可复核代码结构、交互遗漏和画面一致性。所有意见由 GPT 分类为阻塞、重要、一般或建议，并逐项处理。

### 阶段 6：测试与页面验收

**GPT `opencode-go/gpt-6-luna` 组织、执行测试；Gemini `google/gemini-3.1-pro-preview` 复核物理案例。**

#### 物理测试矩阵

至少覆盖：

- 默认参数和常见场景；
- 参数上下限及等号临界值两侧；
- 初速度、力或场方向反转；
- 质量、摩擦系数、角度、间距等参数改变；
- 状态切换、边界、停止或离开场景；
- 守恒量、能量收支、图像斜率/面积等可量化结果。

每个用例写清输入和预期值/判据；测试源码中的断言不等于实际通过，必须在当前候选版本执行并记录结果。

#### 技术与视觉验收

- HTML/JavaScript 语法检查；
- 浏览器运行检查：控制台错误、动画控制、参数联动、重置和图像更新；
- 至少检查桌面、约 800px 平板/窄桌面、约 390–420px 手机视口；
- 检查画布、矢量、标签、图表和控件是否裁切、重叠或过小；保存桌面和窄屏截图供人工复核；
- 确认页面无需后台服务即可本地打开运行。

**本阶段输出：**测试记录（版本/提交 SHA、命令、通过/失败数量、浏览器错误数、未运行项）和截图。未测项目明确记为“未运行”，不能记为通过。

### 阶段 7：JEV 结构化复核

**模型：JEV `jev-1.13`。**本阶段在网页已实现、GPT 已实际运行测试之后进行，不能在测试之前把预计结果当成测试证据。

JEV 不能直接打开 URL 或执行 HTML。调用前由 GPT 准备客观 `state`，包含模型假设和公式、页面文字、关键代码片段、界面截图的文字化描述，以及阶段6实际运行的测试和结果。问题拆成独立命题，例如：

- 物理公式和方向约定是否自洽？
- 页面给出的参数范围是否会产生违反模型假设的状态？
- 动画文字、公式、实时读数和图像是否相互一致？
- 测试是否覆盖关键临界状态？
- 证据中是否存在明确未满足的验收条款？

根据问题使用 `noul`（是/否）、`choice`（分类）或 `score`（量表评分）。JEV 只返回结构化数值，不返回推理；结果不确定或置信度低时标记待人工核对。JEV 结论只能生成复查项，**不能作为物理正确或网页通过验收的证明**。若发现问题，GPT 回到对应阶段修复，再重跑相关测试并更新 JEV 证据。

具体调用方式和限制见 `docs/jev-model-usage.md`：用 System One 对应端点；不要把 JEV 当作 chat 模型调用；密钥只从环境变量读取，不写入代码或文档。

#### JEV 调用说明（每个网页必须执行）

##### 1. 模型和协议

- 固定付费模型 ID：`jev-1.13`。
- 请求端点：`https://opencode.ai/zen/v1/systemone`。
- 认证：请求头使用 `Authorization: Bearer $OPENCODE_API_KEY`；密钥只从环境变量读取，不得写入 JSON、脚本、网页或文档。
- JEV 是结构化问题评估模型，不是对话或代码生成模型。不得使用 chat/completions、responses、messages 协议，也不得用 `opencode run -m ...` 调用。
- `jev-1.13-free` 只限 OpenCode 内部使用；本工作流固定使用 `jev-1.13`。

##### 2. 准备 `state` 和问题

JEV 不会打开 URL、运行 HTML 或直接查看浏览器页面。GPT 必须先把当前候选版本的事实整理成文本 `state`，至少包括教材归属、物理假设与公式、页面实际显示的文字/数值、关键代码逻辑摘要、验收要求和阶段6实际运行的测试结果。可附截图的文字描述，但不能只给网页链接，也不能把未运行的测试写成通过。

问题必须拆成独立、可判断的命题。一个请求可并行提出多个问题，常用类型如下：

| 类型 | 用途 | 请求字段 | 结果读取 |
|---|---|---|---|
| `noul` | 是/否判断 | `instructions` | `noul` 为 0–1，越接近 1 越倾向“是” |
| `choice` | 分类/多选一 | `instructions`、`criteria`（选项 ID 到说明的对象） | 读取 `choice`，并检查 `probabilities` 是否接近 |
| `score` | 量表评分 | `instructions`、`criteria`（从低到高排列的数组） | 读取 `score`、`confidence` 和 `probabilities`；分数范围为 0 至选项数减 1 |

请求体示例（正式调用时将 `state` 替换为本页实际证据）：

```json
{
  "model": "jev-1.13",
  "state": "教材模型、物理假设、实际页面文字和测试结果……",
  "questions": {
    "physics_consistent": {
      "type": "noul",
      "instructions": "页面公式、正方向和实际动画状态是否物理自洽？"
    },
    "issue_type": {
      "type": "choice",
      "instructions": "若存在明确问题，主要属于哪一类？",
      "criteria": {
        "physics": "公式、受力、方向或临界状态错误",
        "interaction": "播放、参数、重置或图表联动错误",
        "layout": "遮挡、裁切或响应式可读性问题",
        "none": "给定证据中没有明确问题"
      }
    },
    "teaching_clarity": {
      "type": "score",
      "instructions": "动画是否清楚呈现本模型的教学重点？",
      "criteria": ["不清楚", "较难理解", "基本清楚", "清楚", "非常清楚"]
    }
  }
}
```

##### 3. 发送请求

请求内容较长时先用 UTF-8 保存为 JSON 文件，再通过 `--data-binary @文件` 发送，避免中文转义和命令行长度问题：

```bash
curl -sS --max-time 300 https://opencode.ai/zen/v1/systemone \
  -H "Authorization: Bearer ${OPENCODE_API_KEY}" \
  -H "Content-Type: application/json" \
  --data-binary @/tmp/opencode/jev_req.json
```

请求 JSON 可用 Python `json.dump(..., ensure_ascii=False)` 生成。不得把真实 API 密钥放入请求文件。

##### 4. 读取结果、处理不确定项

返回是 JSON，包含 `answers` 和 `usage`。`noul` 读取 `noul`；`choice` 读取 `choice` 与对应概率；`score` 读取 `score`、`confidence` 和概率分布。若 `confidence` 或最高选项概率低于约 0.5，或不同选项概率接近，则标注为“不确定”，由 GPT 和人工结合公式、页面及测试复核。JEV 不提供理由，不能替它编造解释，也不能把评分当成“测试通过”。

##### 5. 错误处理与归档

- `ModelProtocolUnsupported`：检查是否误用了对话端点，改用 `/zen/v1/systemone`。
- `FreeTierError`：检查是否在 OpenCode 外调用了免费版；本流程使用 `jev-1.13`。
- `UnknownError` / 服务端错误：检查请求格式，使用 `curl` 直连 System One；仍失败时记录错误并标为“JEV 未完成”，不得跳过后宣布流程通过。
- 401/403：检查环境变量和账号权限，不要把密钥贴入对话或文档。

将无密钥的 `state/questions` 请求和完整 JSON 回答保存到 `docs/models/reviews/<slug>-jev.json`；主文档记录评估结论、人工判断、采纳/拒绝理由。若据此修复网页，必须重跑对应测试并更新 JEV 证据。

详细协议备忘仍见 `docs/jev-model-usage.md`；本节是每个网页制作流程中的强制操作步骤。

### 阶段 8：整理、导航与交付

1. GPT 检查页面标题、文件名、公式单位、说明文字和 PRD 一致。
2. 在项目 `index.html` 增加演示卡片，标题、简介和链接对应实际模型页面。
3. 按现有交付习惯，将页面和导航更新同步到 `_repo`；同步前后比较文件差异，防止旧版本覆盖新版本。
4. 检查 Git 状态和改动范围，只包含本次页面、导航、需求和必要测试文件。
5. 记录最终验收状态与未解决事项；经确认后再提交/推送，不把 JEV 的评分直接写成测试通过。

**最终交付包：**独立 HTML、需求/验收文档、测试记录、桌面/手机截图、导航卡片及版本信息。

## 4. 每个网页的阶段文档要求

为每个模型建立一个主文档：`docs/models/<slug>.md`，例如 `docs/models/horizontal-conveyor-belt.md`。这份文档是该页面唯一的需求与验收事实来源。**不为每次 GPT/Gemini/GLM 对话另存一份重复文档**，只把结论、决定和可复核证据写回主文档。

| 阶段 | 是否产出阶段文档 | 写入内容/位置 |
|---|---|---|
| 选题与查重 | 建立主文档骨架，不另写选题报告 | 更新总模型清单中的状态/页面路径；主文档记录清单编号、教材位置、已有网页和查重结论。 |
| 教材与物理模型定稿 | 必须 | 主文档“教材对应与物理规格”节：教材版本/章节、课内或拓展、假设、变量、方程、边界和临界状态。 |
| PRD 与验收设计 | 必须 | 同一主文档“产品需求”与“验收矩阵”节；锁定目标、非目标、交互、参数和预期值。 |
| 画面与交互方案 | 必须记录，不另建文件 | 同一主文档“画面/交互”节：页面区块顺序、动画状态、控件、图表和手机布局。GLM 草图只保存最终采纳结论，不存多轮草稿。 |
| 编码实现 | 通常不另建文档 | 代码、PRD 和版本控制差异为记录；若实现偏离规格，在主文档的“变更记录”写原因并同步修订验收条件。 |
| Gemini/GLM 审阅 | 必须留摘要 | 主文档“独立审阅与处理”节：审阅者/固定版本、问题、严重级别、采纳/拒绝及理由。不要保存冗长原始对话。 |
| 物理/浏览器验收 | 必须 | 主文档写实际执行命令、版本/提交 SHA、通过/失败数、控制台错误数及未运行项；截图存 `docs/models/artifacts/<slug>/`。 |
| JEV 复核（测试之后） | 必须留结构化证据 | 将无密钥的请求 `state/questions` 和完整 JSON 回答保存为 `docs/models/reviews/<slug>-jev.json`；主文档记结论和人工处理。若调用失败，记录失败并阻止标为完成。 |
| 导航与发布 | 必须更新已有文件，不另建报告 | 更新 `index.html` 卡片；同步 `_repo`；主文档补最终文件路径、版本和交付状态。提交/推送依用户确认执行。 |

### 主文档固定结构

1. 模型编号、slug、教材册/章节、课内/拓展状态、查重结果；
2. 冻结的物理规格与公式；
3. PRD、非目标和参数范围；
4. 动画状态、界面区块、图表及响应式规则；
5. 验收矩阵（输入、预期结果、边界和临界项）；
6. Gemini/GLM/JEV 审阅记录及决策；
7. 实测结果、截图/日志路径、版本信息和变更记录。

**每个模型至少要有：一个主文档 + 一份 JEV JSON + 实测验收结果。**原始对话不作为交付文档；测试截图/日志按实际执行情况保存，不能用计划代替结果。

## 5. 可复用的模型提示模板

### GPT `opencode-go/gpt-6-luna`：物理模型规格与 PRD

> 根据人教版【册/章/节】及模型清单【编号/名称】，为一个独立动画网页建立物理规格。列出研究对象、理想化条件、正方向、状态方程、分阶段公式、边界和临界条件、可调参数、显示量、图像、典型误区与可量化验收案例。明确教材内容与拓展内容，不要开始写代码；对不确定的教材归属标出待核查项。

### Gemini `google/gemini-3.1-pro-preview`：独立物理与教学审阅

> 请独立审核以下模型说明，不要默认作者正确。逐条检查公式推导、正负号、受力方向、临界条件、边界状态和量纲；给出至少一个可能出错的边界/反例。另指出哪些属于人教版正文，哪些属于常见高考拓展。每项意见需给理由和可复核公式，不要泛泛评价。

### GLM `opencode-go/glm-5.3`：限定范围的 UI/代码任务

> 只处理【组件/文件/页面区块】。不得修改下列已锁定物理公式与状态定义：【粘贴】。输出【布局草案/补丁/组件】，遵守【现有网页样式、响应式要求、控件行为】；列出改动文件、实现点、未完成项和建议测试。不要重写或覆盖未指定文件。

### JEV `jev-1.13`：结构化验收问题

为 `state` 提供中立的模型说明、网页文字/关键代码摘要和实际测试结果；每个问题只问一项。可用 `noul` 判断“公式是否自洽”，用 `choice` 将风险分类为“物理/交互/布局/无明确问题”，用 `score` 评价教学可读性。低置信或概率接近时列为人工复核，不将数值结果解释成 JEV 给出的理由。
